# IDD-0006.spec-forward-keyset-pagination

## Intent

Provide forward-only keyset pagination over immutable LINQ and EF Core specifications without intermediate materialization or loss of typed cursor values.

## Behavior

- `SeekAfter(value)` uses one sorting key; `SeekAfter((a,b,...))` uses a typed tuple with 2–7 cursor keys. Keys must match the number, sequence and exact CLR types of the contiguous primary `OrderBy`/`ThenBy` block. Validation occurs while building the specification.
- Accepted non-nullable key types are `byte`, `short`, `int`, `long`, `decimal`, `DateTime` and `DateOnly`. `string`, `Guid`, nullable keys, `object`-boxed values and custom comparator keys are not supported. A cursor is not accepted without an immediately preceding ordering block in its current typed stage.
- The boundary is exclusive: the row represented by the cursor is excluded. For ascending keys, the corresponding comparison is greater-than; for descending keys, less-than. Multiple keys combine lexicographically, including mixed ASC/DESC and ties.
- The seek filter applies to the input of its ordering block *before* ordering, `Take`, or projection. A cursor combined through `And`/`Or` filters the entire combined predicate, not merely one side of `Or`.
- `SeekAfter` cannot follow `Take` in the same stage; `Skip` and `SeekAfter` are mutually exclusive, including when specifications are composed. A cursor cannot be duplicated or followed by additional sorting keys within the same stage. A subsequent projection creates a new stage that may have its own independent ordering and cursor.
- Caller-supplied ordering must be **unique and deterministic**, typically ending with a unique ID, to avoid skips or duplicates in pagination. The library does not infer uniqueness or database indexes.
- Cursor values and selectors remain strongly typed; construction avoids boxing in library-owned cursor storage and does not compile expressions or force LINQ-to-Objects evaluation. Database-side SQL translation, collation and indexing are provider-dependent; boundary comparisons should be parameterizable for EF Core execution.
- No reverse paging, cursor token serialization or token generation is included. Concurrent inserts/deletes do not offer snapshot consistency; callers must arrange an appropriate transaction/isolation level when required.

## Acceptance Criteria

- Correct next-page results for one to seven keys, mixed directions, equal-prefix ties and successive pages.
- The boundary row is never included, and missing/mismatched/unsupported keys fail at configuration time.
- Seek-before-order semantics survive source composition and typed projections.
- No unexpected `Skip`/cursor combination or repeated cursor is accepted.
- EF Core SQL translation remains deferred without client-side filtering on supported providers.

## Verification

Test lexicographic ordering and exclusive boundaries in LINQ and SQLite; reject wrong type/arity, unsupported keys, missing/improper order, repeated seek, `Skip` conflicts and `Take` before seek. Inspect SQL for filtering, ordering and absence of offset-based paging in supported scenarios. Verify provider limitations without assuming snapshot guarantees.
