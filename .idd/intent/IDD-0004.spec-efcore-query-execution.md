# IDD-0004.spec-efcore-query-execution

## Intent

Offer an optional EF Core 10 integration that applies immutable specification rules to existing EF Core queries while preserving the calling query's semantics and EF-specific options.

## Behavior

- The EF Core package depends on the LINQ core package; users may execute `EFCoreSpecification<T>`, `EFCoreProjectedSpecification<TSource,TResult>` and their read-only EF Core interfaces against `DbContext.Set<T>()` or an existing `IQueryable<T>`.
- `DbContext.BySpecification(spec)` and `DbContext.Set<T>().Where(...).BySpecification(spec)` use the same evaluation semantics. Existing input `IQueryable` operators are preserved in their established order; applying the specification is deferred and does not materialize the intermediate query. The result type follows any projection.
- EF-only queryable application requires an EF Core compatible asynchronous query provider and rejects LINQ-to-Objects `EnumerableQuery` instead of silently ignoring EF-only settings. Ordinary in-memory queries use core specifications.
- Root EF options support `AsTracking`, `AsNoTracking`, `AsNoTrackingWithIdentityResolution`, `AsSingleQuery`, `AsSplitQuery`, `IgnoreAutoIncludes`, `IgnoreQueryFilters`, `TagWith`, `TagWithCallSite`, and navigation Includes (IDD-0005).
- Tracking and splitting each have a default mode (inherit context behavior) or one explicitly selected mode. Last setter within a specification wins. Equal explicit modes and defaults can compose; incompatible explicit modes from independent operands fail immediately.
- EF Core 10 named global filters can be selectively disabled using their exact names; names accumulate without duplicates across repeated configuration and composition. Disabling all global filters takes precedence. Applied exclusions affect the entire resulting query, not just one `Or` branch. A configured filter name is not validated against the EF model when building the specification.
- Disabling tenant or other security-critical global filters is potentially data-exposing. These options are **not authorization controls**: trusted application code must decide which filters may be disabled.
- `Search(selector, pattern)` adds an EF-translatable SQL `LIKE` predicate to root or projected stages. `% ` and `_` wildcards follow SQL conventions (`%` any sequence, `_` one character); escaping, case sensitivity and collation are provider-specific. No implicit wildcard insertion or automatic substring matching occurs; provider translation is required.
- Tags are appended in order (including duplicates in specification state), whitespace-only tags are ignored, null tags rejected; the EF provider may normalize repeated SQL comments. `TagWithCallSite` emits source call-site information that can expose the file path in generated SQL.
- Conditional EF options and Include operations add nothing when disabled; invalid non-null arguments remain invalid even for disabled operations.
- `PipelineSteps` and the read-only EF option diagnostics expose query behavior for inspection, but the diagnostics are not executable configuration. `BySpecificationCriteria` has the narrower behavior defined in IDD-0003.

## Non-goals

- Ensuring every valid LINQ expression translates on every EF Core database provider.
- Making query-filter bypass a security/authorization decision.
- Executing EF-specific query options against ordinary LINQ-to-Objects providers.

## Acceptance Criteria

- A specification can extend an already filtered/paged EF query without overwriting previous operators.
- Provider validation rejects incompatible `IQueryable` inputs immediately.
- Root and projected EF queries retain correct types and apply expected tracking, filters, SQL LIKE, splitting and tags where supported.
- Named and all-filter disabling match EF Core semantics without altering unrelated filters.
- EF query evaluation remains deferred until the caller enumerates it.

## Verification

Verify EF Core SQLite translation and results for upstream query operations, source and projected specifications, no-tracking/tracking, named filters, SQL search, call-site tags and provider rejection. Cover security-sensitive named filter behavior.
